# TIL — GitHub 처음 사용하기 (커밋 & 푸시)
날짜: 2026-08-10 · 주제: Git/GitHub 첫 사용, commit, push

## 오늘 배운 것 (요약)
- **Git**은 로컬에서 돌아가는 **버전 관리 도구**, **GitHub**는 그 저장소를 올려 공유·백업·협업하는 **원격 공간**.
- 작업 흐름은 **3단계 영역**을 지난다: 작업 폴더 → (`git add`) 스테이지 → (`git commit`) 저장소 → (`git push`) 원격.
- **`git init`** = 폴더를 Git 저장소로 만드는 첫 명령(`.git` 폴더 생성, 프로젝트당 1회).
- **커밋** = 각 시점의 스냅샷을 이력에 쌓는 세이브 포인트. 메시지는 "무엇을/왜 바꿨는지" 구체적으로.
- **커밋은 로컬에만** 있고, **push**로 GitHub에 올린다.
- **첫 push는** 브랜치 연결이 없어서 오류가 나며, `git push -u origin main`으로 한 번 짝지어 주면 이후엔 `git push`만으로 된다.

## 새 프로젝트 처음부터 푸시까지 — 순서 치트시트
> "새 환경에서 처음부터 세팅"이 걱정될 때 이 순서 그대로 따라 하면 됨.

1. GitHub 웹에서 **새 repository 생성** (빈 저장소로).
2. 내 프로젝트 폴더에서 터미널 열기.
3. `git init` — 저장소 초기화 (`.git` 생성).
4. `git add .` — 바뀐 파일 전부 스테이지에 담기.
5. `git commit -m "first commit"` — 스냅샷 기록(메시지 필수).
6. `git remote add origin <GitHub 저장소 주소>` — 원격 연결(주소는 GitHub 저장소 페이지에서 복사).
7. `git branch -M main` — 기본 브랜치 이름을 main으로.
8. `git push -u origin main` — **첫 푸시**(원격과 짝지어 업로드). 이후부터는 `git push`.

## 자주 쓰는 명령 요약
| 명령 | 하는 일 |
|------|---------|
| `git status` | 지금 어떤 파일이 바뀌었는지 / 스테이지 상태 확인 |
| `git add .` | 바뀐 것 전부 스테이지에 담기 |
| `git commit -m "메시지"` | 스테이지의 내용을 스냅샷으로 기록 |
| `git push` | 로컬 커밋을 원격(GitHub)으로 올리기 |
| `git pull` | 원격의 변경을 로컬로 내려받기 |
| `git log --oneline` | 커밋 이력 한 줄씩 보기 |

## Q&A 로그

### Q1. Git과 GitHub의 차이
- 내 답: "깃은 저장을 하는 도구고, 깃허브는 그걸 공유하는 곳이다."
- 보완: Git은 단순 저장이 아니라 **버전 관리 도구**(변경 이력을 스냅샷으로 기록, 로컬에서 동작). GitHub는 Git 저장소를 **클라우드에 올려 공유·백업·협업**하는 원격 공간.

### Q2. 맨 처음 한 일 — `git init`
- 내 답: "git init을 먼저 했다. 그런데 자세히는 이해 못 함."
- 보완 (git init 정리):
  - 현재 폴더를 **Git이 추적하는 저장소로 만드는** 명령.
  - 실행 시 숨김 폴더 **`.git`** 생성 → 모든 버전 이력·설정 저장 (이게 저장소의 실체).
  - 평범한 폴더 → 버전 관리 프로젝트로 승격.
  - **프로젝트당 한 번만** 실행.
  - 확인: `ls -a` 로 `.git` 폴더 보이면 성공.

### Q3. 스테이지 & `git add`
- 내 답: "git add는 직접 쓰진 않았지만, 커밋 전에 스테이지에 올린다는 건 알고 있다."
- 보완 (3단계 영역):
  1. **작업 폴더** — 파일을 실제로 수정하는 곳
  2. **스테이지** — 이번 커밋에 넣을 것을 골라 담는 대기 공간
  3. **저장소** — 커밋으로 확정 기록되는 곳
  - `git add`는 1 → 2 이동. `git add 파일명`(특정 파일), `git add .`(전체).
  - 스테이지가 있는 이유: 바꾼 것 중 **원하는 것만 골라** 커밋하기 위해.
  - GUI(VS Code/GitHub Desktop)에서 체크로 담으면 내부적으로 `git add` 수행됨.

### Q4. 커밋(commit)이란
- 내 답: "세이브와 같은 개념. 수정·추가될 때마다 다른 이름으로 저장하듯 계속 쌓아 저장. 무엇을 수정/추가했는지 알기 위해 메시지를 적는다."
- 보완:
  - 파일명이 늘어나는 게 아니라, 파일은 그대로 두고 **각 시점의 스냅샷을 이력에 기록**. 각 커밋엔 고유 ID(해시)가 붙어 되돌리기·비교 가능.
  - 메시지는 구체적으로 ("수정함" ❌ → "PDF 저장 기능 추가" ✅).
  - **커밋은 아직 로컬에만** 존재 → GitHub에 올리려면 push 필요.

### Q5. 푸시(push) & 첫 푸시 오류
- 내 답: "git push 했는데 처음에 'set 뭐시기' 오류가 났고, 해결한 뒤로는 git push로 쉽게 푸시했다."
- 보완:
  - push = 로컬 커밋들을 **원격(GitHub)으로 올려보내는** 동작. (내려받기는 `pull`)
  - 오류 정체: `fatal: The current branch has no upstream branch` → 로컬 브랜치가 원격의 어느 브랜치로 갈지 안 정해져서 (첫 푸시라 연결 상대 없음).
  - 해결: `git push -u origin main` (`-u` = `--set-upstream`).
    - `origin` = 원격 저장소 별명(GitHub 주소), `main` = 브랜치 이름.
    - 로컬 main ↔ 원격 main을 짝지어 줌(upstream 설정). **한 번만** 하면 이후엔 `git push`만으로 됨.
  - (그 전 단계) `git remote add origin <주소>` 로 GitHub 저장소 주소를 로컬에 연결.

### Q6. 오늘의 회고
- 내 답: "전반적으로 완벽히 이해하진 못했지만, **실행 방법론은 이해**해서 다음에 push는 또 할 수 있을 것 같다. 다만 **새 환경에서 처음부터 세팅**하라면 버벅거릴 것 같다."
- 정리: 개념의 '원리'보다 '절차'를 먼저 체득한 건 자연스러운 첫 단계. 위의 **치트시트**를 그대로 따라 하면 새 환경 세팅도 해결됨. 반복하면서 각 단계가 왜 필요한지 자연히 붙는다.
- 다음에 해볼 것: `git status`를 단계마다 찍어보며 파일이 3영역을 어떻게 이동하는지 눈으로 확인 → 원리 이해가 빨라짐.
